# Руководство пользователя: Transformer / KAN

Проект обучает surrogate-модели для численного «чёрного ящика»:

```text
model(inputs) ≈ black_box(inputs)
```

Основной интерфейс – GUI на `egui`; CLI равноправен для автоматизации и
воспроизводимых прогонов. Полный список кратких команд есть в
[README.md](README.md).

## Запуск

Нужен стабильный Rust toolchain.

```bash
cargo build --release
./target/release/transformer          # GUI
./target/release/transformer gui      # GUI явно
```

Для headless CLI без зависимостей GUI:

```bash
cargo build --release --no-default-features
```

Фичи `gui` и `demo` независимы и обе включены по умолчанию. `demo` — это
встроенные чёрные ящики, char-LM, подкоманда `demo` и раздел «Демо» в
интерфейсе; без неё этого кода в бинаре нет, а команда `demo` честно отвечает,
что собрана без демонстраций. `gui` от `demo` не зависит, поэтому рабочая
сборка для пользователя выглядит так:

```bash
cargo build --release --no-default-features --features gui
```

С демонстрациями доступен короткий прогон без своих данных:

```bash
cargo build --release --no-default-features --features demo
./target/release/transformer demo train sum --epochs 5
```

## Данные и `.tnum`

Одна строка исходной таблицы имеет вид:

```text
x0 x1 ... xN y0 y1 ... yM
```

Continuous-входы нормализуются по train-части z-score преобразованием;
категориальные входы остаются целыми кодами. Выходы всегда нормализуются на
время обучения и возвращаются в исходные единицы для метрик и предсказаний.

Подготовка таблицы:

```bash
./target/release/transformer prepare raw.xlsx train.tnum \
  --inputs 10 --outputs 3 --has-header
```

`prepare` и блок **Конвертация в .tnum** раздела GUI «Данные» принимают CSV,
TSV, пробельные таблицы и Excel
(`.xlsx`, `.xlsm`, `.xlsb`, `.xls`, `.ods`). Для текстовых таблиц пустые строки
и комментарии после `#` пропускаются, но пустые **ячейки** сохраняются: `1,,3`
остаётся тремя колонками, и пропуск виден как пропуск, а не как сдвиг данных.
Ошибки называют файл, строку (как она пронумерована в файле, с учётом
заголовка) и имя колонки. Входы-категории задаются так:

```bash
--categorical 2:5,7:3
```

Здесь `x2` содержит коды `0..4`, а `x7` – коды `0..2`. Коды обязаны быть
целыми и находиться в указанном диапазоне. Если заголовок имеет схему
`x0,x1,...,y0,y1`, подготовка умеет определить число входов, выходов и простые
поля вроде `material_id` автоматически.

### Формат файла

`prepare` пишет **TRNUM2** — он хранит не только типы колонок, но и их имена,
единицы измерения и подписи уровней категорий:

```text
TRNUM2
inputs 2
outputs 1
specs C K:3
names "температура" "материал" "влажность"
units "°C" - "%"
levels 1 "песок" "глина" "торф"
rows 2
data
80 0 12.5
60 2 18.1
```

Строковые поля всегда в кавычках: имя может содержать пробелы, Unicode, `#` и
даже совпадать с директивой формата (`"rows"`). Внутри кавычек доступны `\"`,
`\\`, `\n`, `\r` и `\t`; вне кавычек `#` начинает комментарий до конца строки.
В `units` голый дефис означает «единицы нет». Секция `levels` обязательна для
каждого входа `K:n` — файл с `K:n` без подписей считается испорченным, а не
поводом выдумать названия.

**TRNUM1 читается по-прежнему.** Имён в нём нет, поэтому схема достраивается
синтетически: `x0…xN → y0…yM`, а категориальные входы сохраняют тип, получая
подписями свои же коды `"0"…"n-1"`.

`prepare` сохраняет имена из заголовка исходной таблицы. Если заголовка нет,
используются синтетические `x0…xN → y0…yM`. Единицы измерения и настоящие
подписи категорий появятся вместе с диалогом разметки колонок; пока категории
получают подписи-коды `"0"…"n-1"`.

## Архитектуры

Выбор производится флагом `--model-kind transformer|mlp|kan` или в разделе
**Обучение**.

| Модель | Когда начинать с неё | Основные параметры |
| --- | --- | --- |
| Transformer | сложные табличные зависимости, Fourier-кодирование | `d_model`, `heads`, `layers`, `d_ff`, value encoder |
| MLP | сильный простой baseline для фиксированного числа числовых входов | `mlp-width`, `mlp-layers` |
| KAN | важна компактность и интерпретируемость функций | `kan-width`, `kan-layers`, `kan-grid` |

`value-encoder linear|mlp|fourier` доступен только Transformer. Для MLP и KAN
он принудительно линейный: неподходящий флаг является ошибкой, а не молча
игнорируется.

### KAN

В KAN нелинейность расположена на ребре, а не в фиксированной активации узла:

```text
φ(x) = w_base · gelu(x) + Σ_t w_spline,t · B_t(x)
```

`B_t` – кубические B-сплайны на сетке `[-3, 3]` в нормализованном пространстве.
Базовая ветка `gelu` даёт гладкую экстраполяцию за пределами сплайн-сетки.

Типичный CLI-проход:

```bash
./target/release/transformer train train.tnum \
  --model-kind kan --kan-width 16 --kan-layers 2 --kan-grid 16 \
  --lr 3e-3 --epochs 80 --seed 0 \
  --interpret --kan-symbolic --model model-kan.bin
```

`--interpret` — это **версионируемый профиль** конвейера, а не непрозрачная
галочка. Он задаёт четыре параметра (`L1 1e-3`, `prune 0.05`, `fine-tune 20`,
структурное сжатие), печатает их фактические значения перед запуском и
сохраняет их в checkpoint отдельной секцией: через полгода видно, с каким
порогом модель стала такой.

Явные флаги **переопределяют** профиль:

```bash
--interpret --kan-prune 0.3 --kan-finetune-epochs 3
# Конвейер интерпретации v1: L1 0.001, prune 0.3, fine-tune 3 эпох, структурное сжатие
```

Без `--interpret` работают только перечисленные флаги — как раньше:

```bash
--kan-l1 1e-4
# Конвейер интерпретации v1: L1 0.0001, без прунинга
```

`--kan-symbolic` в профиль **не входит**: формулы считаются лениво, по запросу,
и обучение не меняют.

В GUI тот же конвейер включается флажком «Интерпретируемая KAN, профиль v1»
рядом с параметрами KAN; переопределения спрятаны под «Дополнительно». Конвейер
применяется **в обеих фазах** — и к модели разработки, и к финальной, — поэтому
сохранённая модель совпадает с той, по которой принимались решения. Раздел
«Модель» показывает изменение R² на validation по фазам прунинга и структуру
финальной модели.

Отмена прерывает и дообучение после прунинга: модель остаётся недообученной,
поэтому она не сохраняется, test не открывается и профиль в checkpoint не
записывается.

В поиске профиль **не является осью перебора**: ранжирование конфигураций
происходит до конвейера, а сам конвейер применяется уже к выбранной KAN при
обучении.

Фазы выполняются в таком порядке:

1. `--kan-l1 λ` добавляет activation-L1: среднее `|φ|` каждого ребра по
   реальным активациям всех слоёв.
2. `--kan-prune θ` удаляет рёбра, чья p95-важность ниже `θ` от максимума в
   слое; маска блокирует и вклад, и градиент.
3. `--kan-finetune-epochs N` дообучает оставшиеся рёбра с `λ=0`.
4. `--kan-compact` физически вырезает неиспользуемые скрытые узлы и постоянные
   узлы, сворачивая их вклад в bias следующего слоя. Предсказания не меняются,
   а число параметров уменьшается.
5. `--kan-symbolic` подбирает к активным рёбрам примитивы `x`, `x²`, `x³`,
   `sqrt`, `exp`, `log`, `1/x`, `sin`, `tanh` в аффинной форме
   `a·f(bx+c)+d` и печатает послойные формулы.

Символьные формулы используют **исходные единицы** таблицы: в них можно
подставлять значения прямо из Excel. Внутренние `hK_J` – безразмерные скрытые
узлы. Отчёт показывает R² каждой подгонки и выделяет рёбра с `R² < 0.99`;
поэтому формула всегда сопровождается её измеримой точностью, а не выдаётся за
тождество исходной сети.

## GUI

Окно устроено вокруг двух объектов сессии — активного набора данных и активной
модели. Оба видны в **постоянной шапке** из любого раздела: что открыто, сколько
строк, сколько входов и выходов, как они разделены; какая модель обучена и какая
у неё метрика.
Если модель не подходит к активным данным, шапка объясняет причину — расхождение
имени, порядка, типа или уровней категории. Единицы измерения на совместимость
не влияют: это подпись для отчётов.

Разделов пять.

### Данные

Открытие `.tnum` и таблиц (XLSX/CSV/TSV), диалог разметки, замечания к качеству
таблицы и конвертация в `.tnum`. Для таблицы диалог разметки показывается
всегда: автоопределение только заполняет начальное состояние. После применения
видны первые 20 строк уже размеченного численного представления; категории
показываются подписями, а не внутренними кодами. Здесь же остаётся отчёт о
пропусках, константах и зависимых входах, включая найденный симплекс.

Стратегия разбиения задаётся здесь же: holdout с долями train/validation/test и
seed либо K-fold с отдельным отложенным test. Некорректное разбиение
блокирует запуск до исправления. При K-fold одиночная development-модель не
строится: конфигурацию оценивают через «Авто» или «Свою сетку», после чего
выбранную строку обучают финально.

### Обучение

Три режима: **Одна конфигурация** (ручные гиперпараметры), **Авто** (готовый
бюджет поиска) и **Своя сетка**. Поиск, выбор строки и финальное обучение живут
на одном экране и работают с активным набором данных.

Кривая обучения — настройка, а не отдельный сценарий: поле «validation каждые N
эпох» включает замеры по ходу обучения, рядом рисуется R²(validation) и
рекомендованная точка остановки. Отдельного экрана Epoch-sweep больше нет.
Долгие операции выполняются в worker-потоке; отмена не удаляет уже активную
модель и не приписывает ей метрики незавершённого запуска.

Сценарий двухшаговый и одинаковый во всех трёх режимах.

1. **Проверить конфигурацию** — обучение фазы разработки и конвейер
   интерпретации; test не трогается. При holdout это одна модель с метриками на
   validation, при K-fold — обучение на каждом fold и CV-оценка: одна модель
   произвольного fold оценкой не является. Рядом со средним показывается
   разброс R² между folds.
2. **Зафиксировать и обучить финально** — переобучение на train + validation с
   заранее заданным `final_init_seed` и единственный замер на test.

Второй шаг включается только при точном совпадении с проверенным кандидатом.
Кандидат — это конфигурация модели, параметры обучения и профиль интерпретации
вместе с разбиением и ревизией данных; правка любого поля делает проверку
устаревшей, и причина написана рядом с недоступной кнопкой.

Test открывается один раз **на набор данных**, а не на конфигурацию: после
первого замера другой кандидат на той же ревизии к финальному обучению не
допускается, а повторный запрос того же кандидата показывает уже полученный
результат, не тратя test второй раз. Проверки других кандидатов на validation
при этом разрешены. Новый набор данных начинает жизненный цикл заново. То же
правило проверяется и в worker-потоке: безопасность не зависит от того, что
показывает кнопка.

Ревизия защищает только текущую сессию: повторное открытие того же файла и
перезапуск приложения дают новую ревизию. Честная защита требует отпечатка
данных в checkpoint — это отдельная задача.

После смены набора прежний поиск очищается; после изменения разбиения он
остаётся видимым, но помечается устаревшим и к проверке не допускается.

### Модель

Подразделы: **Итоги** (происхождение модели, метрики, единственный замер на test,
сохранение), **Кривые KAN**, **Формулы** и **Диагностика**. В итогах показаны
агрегат и метрики каждого выхода, схема разбиения и seed, а также чем является
сама модель: отладочной (обучена на train, validation осталась вне обучения),
финальной (train + validation) или загруженной из файла. Кнопка сохранения
называет то, что сохранит, — отладочную модель нельзя молча выдать за результат
работы. Checkpoint не хранит
эти оценки: после загрузки файла UI не переносит на него числа предыдущей
модели.

**Чувствительность** считается по парам РЕАЛЬНЫХ строк, а не независимым
возмущением входов. Причина в связях внутри данных: если доли состава дают
постоянную сумму, сдвиг одной координаты уводит точку с многообразия, и модель
спрашивают о том, чего в задаче не существует. Поэтому вторая точка пары —
ближайшая реальная строка с теми же категориями, а шаг равен
`x₂ = x + α(neighbor − x)`; расстояние считается только по непрерывным входам.

Категориальные входы не возмущаются вовсе — дробный шаг по коду не имеет
смысла, — и их число выводится отдельной строкой. Дискретные переходы между
уровнями это не заменяет: они станут отдельной метрикой.

Чувствительность **модели** доступна всегда. Чувствительность исходного
процесса — только у встроенных задач, где функцию можно вызвать; она считается
на тех же самых парах точек, поэтому числа сравнимы, и рядом печатается
абсолютное расхождение средних. Само по себе значение чувствительности модели
ничего не доказывает: надёжность видна по расхождению вместе с метриками на
validation. Если непрерывных входов нет или пары не находятся, выводится
причина, а не пустое число.

### Прогноз

Единичный прогноз по именам колонок и прогноз по таблице. Внутри это один путь:
короткая форма — пакет из одной строки, поэтому единичный и пакетный расчёт не
могут разойтись.

Колонки таблицы связываются **по именам входов из схемы модели**; у модели без
имён это по-прежнему `x0…xN`. Порядок колонок в файле значения не имеет.
Выходные колонки называются по схеме: существующие заменяются, отсутствующие
добавляются справа, посторонние колонки переносятся как значения. Ошибка в
ячейке адресуется номером строки файла и именем колонки.

Операция называется **«Экспортировать таблицу с прогнозами»** именно потому,
что результат — новая минимальная книга со значениями: стили, формулы, другие
листы и структура исходного файла не сохраняются.

### Демо

Встроенные black-box задачи как источник данных и char-level LM. К рабочему
сценарию они не относятся и держатся отдельно.

## CLI

Все подкоманды запускаются так:

```bash
./target/release/transformer <command> ...
```

### Обучение и предсказание

```bash
# Свой .tnum
./target/release/transformer train train.tnum \
  --model-kind mlp --mlp-width 128 --mlp-layers 3 \
  --epochs 80 --lr 1e-3 --model model.bin

# Или сразу таблица — .xlsx, .csv, .tsv
./target/release/transformer train raw.xlsx --model-kind mlp --epochs 80

# Встроенная задача — только через demo
./target/release/transformer demo train projectile --epochs 40 --model projectile.bin

# Инференс в исходных единицах — одна строка или таблица целиком
./target/release/transformer predict model.bin 0.25 0.75
./target/release/transformer predict model.bin --table вход.xlsx --out прогноз.xlsx
```

`train` принимает только файл — `.tnum` или обычную таблицу; встроенные задачи
живут отдельно, в `demo train`, поэтому `train sum` — ошибка с подсказкой, а не
молчаливая подмена данных. Для таблицы разметка
определяется тем же автоопределением, что и в `prepare` (заголовок вида
`x…/y…`); если его не хватает, ошибка отправляет к `prepare`, где роли колонок
задаются флагами. Промежуточный `.tnum` при этом не создаётся — таблица
превращается в датасет напрямую.

Общие флаги: `--epochs`, `--eval-every`, `--model`, `--lr`, `--batch-size`,
`--seed`, `--scheduler constant|warmup-cosine`, `--warmup`, `--min-lr-ratio` и
`--diagnose`. CLI строго отвергает неизвестные и несовместимые флаги.

### Поиск по сетке

```bash
./target/release/transformer search train.tnum \
  --model-kinds transformer,mlp,kan \
  --d-models 32,64 --layers-list 2 \
  --mlp-widths 64,128 --mlp-layers-list 3 \
  --kan-widths 8,16 --kan-layers-list 2 --kan-grids 8,16 \
  --lrs 1e-3,3e-3 --epochs 80 --batch-size 64 --seeds 0,1

# То же на встроенной задаче
./target/release/transformer demo search projectile --model-kinds mlp,kan
```

Цена перебора печатается до запуска, метрики — только с validation (или CV), а
первая строка ранжирования и есть рекомендация.

### Кривая по эпохам

Отдельного `epoch-sweep` нет: число эпох выбирается тем же обучением.

```bash
./target/release/transformer train train.tnum \
  --model-kind kan --kan-width 16 --kan-layers 2 --kan-grid 16 \
  --epochs 120 --eval-every 10
```

`--eval-every N` включает замеры validation по ходу обучения и печатает
таблицу, sparklines loss/R² и рекомендованную остановку. Это одно обучение
development-фазы вместо серии независимых, поэтому между точками нет шума от
повторной инициализации. Сохранённая модель всё равно строится отдельным refit
на train+validation с фиксированным `final_init_seed`: кривая помогает выбрать
число эпох, но не является историей весов из checkpoint. Рекомендация сама не
меняет текущий `--epochs`: это диагностическая подсказка, а не скрытая ранняя
остановка.

## Checkpoint-ы

`.bin` – секционный little-endian формат. Он хранит тип модели, конфигурацию,
параметры, спецификации входов, схему данных, нормализаторы и train-диапазоны.
KAN добавляет hard-prune маски, реальные размеры слоёв после compaction и
калибровочную выборку для формул. Невалидные размеры сжатой топологии и
калибровка неверной формы отвергаются при загрузке.

Секция `schema` хранит имена колонок, единицы измерения и подписи уровней
категорий, поэтому эти метаданные не теряются при сохранении и загрузке модели.
Прогноз, поколоночные метрики и KAN-формулы после загрузки `.bin` говорят
именами колонок, а не `x0`/`y0`. Версия формата при этом **не менялась**:
`schema` пишется дополнительно к `feature_specs`, поэтому checkpoint из новой
версии читается старым бинарём, который просто пропустит незнакомую секцию.

Старые checkpoint-ы остаются читаемыми: отсутствие новых KAN-секций означает
старое поведение, а отсутствие `schema` — синтетические имена `x0…xN → y0…yM`
с сохранением категориальных типов (подписями становятся сами коды). Если обе
секции присутствуют и противоречат друг другу, файл считается испорченным и
отвергается — выбирать «более правильную» версию типов недопустимо. После
загрузки старой KAN можно предсказывать; для формул её нужно пересохранить новой
версией после обучения с исходными данными.

## Имена колонок

Если данные пришли из TRNUM2 со схемой, имена используются в поколоночных
метриках, в `predict`, в KAN-формулах и в предупреждениях GUI об
экстраполяции. У модели без имён — старый checkpoint, встроенный чёрный ящик,
TRNUM1 — схема синтетическая, поэтому вывод остаётся прежним:
`x0…xN → y0…yM`.

В CLI категориальный вход задаётся подписью уровня:

```bash
./target/release/transformer predict model.bin 70 глина
```

Неизвестный уровень — ошибка со списком известных, а не молчаливая подстановка
кода. У старых моделей подписями служат сами коды (`"0"`, `"1"`, …), поэтому
прежние команды продолжают работать без изменений.

В формулах имя со спецсимволами берётся в обратные кавычки, иначе
`12·температура, °C` читалось бы как два разных терма.

Тот же `predict` принимает и таблицу целиком:

```bash
./target/release/transformer predict model.bin --table вход.xlsx --out прогноз.xlsx
```

Колонки связываются по именам входов из схемы, порядок в файле не важен, а
отчёт печатает число строк, строки вне обученного диапазона и списки заменённых
и добавленных колонок. Формы не смешиваются: `--table` вместе со значениями
одной строки — ошибка, и оба флага нужны вместе. Как и в GUI, результат —
новая книга только со значениями: стили, формулы и другие листы не сохраняются.

## Категории в MLP и KAN

Embedding категорий есть только у transformer. MLP и KAN получают код категории
как обычное число и неявно считают, что код 3 «между» 2 и 4. Хранение подписей
этого не исправляет, поэтому CLI и GUI выводят предупреждение, если у модели
MLP/KAN есть категориальный вход. Для таких данных выбирайте transformer либо
кодируйте категории заранее.

## Протокол оценки

Данные делятся на три части (по умолчанию holdout 70/15/15, seed разбиения 1):

| Часть | Для чего | Кто её видит |
|---|---|---|
| train | обучение весов | обучение |
| validation | выбор архитектуры, lr, эпох, порога прунинга | поиск, диагностика, KAN-конвейер |
| test | одна финальная оценка | только финальный замер CLI |

Отбор конфигурации идёт **только по validation**: функция поиска физически не
получает test — он живёт в отдельном типе `HoldoutTest`, который отдаёт наружу
метрики, а не данные. В CLI после фазы разработки конфигурация переобучается на
train + validation с заранее заданным `final_init_seed = 0`, и только затем test
открывается один раз. Выбирать seed по результату нельзя: это тот же подбор.

Seed-ы разделены: `data_seed` (генерация демо-данных), seed разбиения,
`init_seed` (инициализация весов и порядок батчей) и `final_init_seed`.

При малых выборках вместо holdout можно взять K-fold: test откладывается сразу,
а поиск идёт по folds на остатке. Нормализаторы при этом обучаются по train
КАЖДОГО fold — validation и test в поисковый `fit` не участвуют. Для финального refit
нормализаторы строятся заново по train+validation; test не участвует. Агрегация
двухуровневая: сначала среднее по folds внутри одного `init_seed`, затем среднее
и std между seed-ами, поэтому `±` всегда означает устойчивость к инициализации.
Разброс R² между folds хранится отдельно как `fold std` и в `±` не попадает.

## Метрики и практический цикл

R² – основная метрика качества. RMSE и MAE измеряются в исходных единицах,
относительная ошибка может быть нестабильной возле нулевого target. Рядом с
каждой метрикой всегда указано её происхождение: validation, cv-N или test.

Практический цикл:

```text
Данные → (Одна конфигурация | Авто | Своя сетка) → Модель → Прогноз
```

Если качество недостаточно, сначала проверьте «Диагностику» и покрытие train-
диапазона, затем сравните все три архитектуры в режиме «Авто» или «Своя сетка». Для
периодических зависимостей Transformer с Fourier-encoder может быть полезен;
для читаемой компактной модели начните с KAN и увеличивайте `kan-grid` раньше,
чем ширину или глубину.

## Старая Python-автоматизация

В `tools/` сохранены legacy-скрипты для совместимости:

| Скрипт | Rust UI/CLI | Что остаётся только в Python |
| --- | --- | --- |
| `tools/prepare_numeric_dataset.py` | Полностью покрыт и расширен: Excel, авто-схема, конвертация в разделе «Данные», строгая валидация `.tnum` | Нет функционального преимущества |
| `tools/epoch_sweep/epoch_sweep.py` | Покрыты одна траектория обучения, таблица и sparklines, рекомендация остановки, live-график GUI | CSV/PNG-артефакты и отдельный `.bin` на каждую контрольную эпоху |

Python epoch-sweep парсит текстовый вывод внешнего бинарника и не знает о
современных KAN-фазах. Используйте Rust-интерфейсы по умолчанию. Legacy-скрипт
имеет смысл только если нужен именно PNG-артефакт или набор checkpoint-ов для
каждой контрольной эпохи.

cargo fmt --check

```

Комбинации фич проверяются отдельно — иначе `gui` незаметно обрастает

cargo test --no-default-features
cargo test --no-default-features --features gui
cargo test --no-default-features --features demo
```

Скрипт создаёт `dist/Transformer.app`, ZIP и DMG, проверяет DMG через
`hdiutil` и берёт версию приложения из `Cargo.toml`. Для обработки иконки
нужен Pillow для `python3`.
